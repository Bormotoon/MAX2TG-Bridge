# Аудит MAX2TG-Bridge

Дата: **18 сентября 2026**.

## 1. Резюме

Проект реализует основной сценарий персонального моста, но **сейчас не обеспечивает надёжную доставку при сбоях**. Главные риски — потеря сообщений после временной ошибки, остановка обработки отдельного чата после реконнекта, дубли при неоднозначном результате отправки и нарушение порядка из-за фоновой отправки альбомов.

Самая важная связка проблем:

1. ID сообщения запоминается **до** обработки и доставки.
2. TelegramSender подавляет окончательные ошибки отправки.
3. Worker считает обработку завершённой даже при исключении.
4. Альбом может существовать только в памяти уже после завершения callback.
5. После сбоя нет durable inbox/outbox, повторной доставки и сверки результата.

Следовательно, текущая дедупликация — это ограниченный кеш **приёма событий**, а не учёт доставленных сообщений. Увеличение размера кеша или перенос единственной операции записи ID в конец callback не решит проблему целиком.

**С чего начать:** устранить отмену worker при обрыве RPC, сделать результат отправки явным, ввести сохраняемый журнал доставки, объединить отправку альбомов и текста в один последовательный исполнитель на чат, добавить deadlines авторизации и корректное завершение процесса.

## 3. Дедупликация и гарантии доставки

### D01 — P0. Сообщение считается обработанным до доставки

**По коду:** `app/max_client.py:294–304, 453–476, 272–287`; `app/tg_sender.py:114–147`; `app/max_listener.py:106–122`.

`_is_duplicate()` сразу добавляет ID в `_seen_ids`, затем сообщение ставится в очередь. Если resolver, создание топика или отправка падает, повторный DISPATCH будет отброшен. `_message_worker()` логирует исключение и делает `task_done()`, но не повторяет доставку. Дополнительно sender после исчерпания попыток возвращает `None`, а публичные send-методы не передают результат вызывающему коду. В логах возможен «Forwarded»/«Posted album» при фактическом провале.

**Сценарий:** принято M → Telegram недоступен → попытки исчерпаны → MAX повторяет M → «already forwarded, skipping». Для альбома callback может завершиться ещё до первой попытки отправки.

**Исправление:** сохраняемый inbox с состояниями `received`, `processing`, `delivered`, `retryable_failed`, `permanent_failed`, `uncertain`. Разделить подавление повторной постановки в очередь и фиксацию успешной доставки. Sender должен возвращать Telegram message IDs либо типизированную ошибку. Для частичной доставки хранить результаты по частям, а не повторять всё сообщение целиком.

### D02 — P1. Ключ дедупликации не содержит аккаунт и чат

**Воспроизведено:** `app/max_client.py:294–304`.

Два сообщения из разных чатов с одинаковым `message_id` считаются одним. **Глобальная уникальность MAX ID в этом аудите не доказана**: наличие дефекта в модели ключей подтверждено, частота его проявления на реальном MAX неизвестна.

**Исправление:** ключ `(max_account_id, normalized_chat_id, message_id)` и отдельный учёт версии события. Для текущего однопользовательского процесса хотя бы `(chat_id, message_id)`.

### D03 — P1. `id: null` становится общим ID `"None"`

**Воспроизведено:** `app/max_client.py:812–825`.

`str(msg_body.get("id", ""))` преобразует JSON null в непустую строку `"None"`. Все следующие события с null будут подавлены. Отсутствующий ID и пустая строка, напротив, вообще не дедуплицируются.

**Исправление:** валидировать ID до преобразования; invalid/missing ID отправлять в диагностический карантин либо применять явно ограниченную fallback-политику. Хеш текста не использовать как универсальный ID: одинаковые сообщения могут быть законными.

### D04 — P1. Нет устойчивости к рестарту; размер кеша не связан с горизонтом replay

**По коду:** `app/max_client.py:106, 138, 294–304`.

Кеш из 2000 записей общий на все чаты и живёт только в памяти. Новый процесс забывает историю. Высокая активность одного чата вытесняет ID остальных. Повтор старого события проходит после вытеснения; при backlog запись может исчезнуть даже до первой доставки, после чего повтор будет поставлен в очередь второй раз.

Кеш называется LRU в документации, но при повторном доступе `move_to_end()` не вызывается: фактически это FIFO по первому появлению уникального ID.

**Исправление:** durable unique constraint для всех незавершённых операций; retention доставленных записей по времени и ожидаемому replay-окну; память использовать только как ускоритель. Сохранение одного голого seen-set без статуса доставки законсервирует D01.

### D05 — P1. Редактирование ошибочно отождествлено с дублем

**По коду:** `app/max_client.py:458–468`; тест `test_same_message_id_is_forwarded_once`.

Отбрасываются любые события с тем же ID: безобидное добавление link-preview, исправление текста, новая подпись и потенциально значимое обновление вложений. Даже если первая версия ещё в очереди, payload не обновляется. Отдельной обработки удаления тоже нет.

**Исправление:** хранить hash нормализованного содержимого/ревизию и связь MAX ID → Telegram message IDs. Идентичный replay подавлять, значимое обновление редактировать в Telegram или отражать явно. Правила игнорирования технических preview отделить от пользовательских правок. Форматы edit/delete в MAX сначала подтвердить захватом протокола.

### D06 — P1. Повторная отправка после timeout может создавать дубли

**По коду, исход зависит от сети:** `app/tg_sender.py:114–129, 266–288`; `app/max_client.py:513–540`.

Telegram мог принять запрос, а клиент — не получить ответ. Безусловный retry отправляет ещё одно сообщение; fallback voice→audio также может дублировать уже доставленное голосовое. В направлении TG→MAX повтор пользователя после предупреждения создаёт новый случайный `cid`, без связи с исходным Telegram update.

**Исправление:** distinguish «точно не отправлено» и «результат неизвестен»; журналировать попытки и подтверждённые IDs. MAX `cid` сохранять стабильным на логическую операцию, но гарантию server-side idempotency проверить экспериментально. Telegram Bot API не даёт универсального idempotency key для sendMessage: обещать строгий exactly-once при потере ответа нельзя. Нужна честная политика для uncertain-состояний и, где возможно, сверка.

### D07 — P2. Антиэхо отсекает все собственные сообщения MAX

**По коду:** `app/max_client.py:828–829`; `app/max_listener.py:505–506`.

Сообщение, вручную отправленное владельцем из нативного MAX, также не попадёт в Telegram. Это шире защиты от эха TG→MAX; такие события ещё и занимают кеш дедупликации.

**Предложение:** документировать выбранное поведение либо подавлять только сообщения, связанные с собственным outbox. Сверять типы sender/account IDs, иначе строковый и числовой ID могут нарушить антиэхо.

## 4. WebSocket, RPC, очереди и жизненный цикл

### R01 — P0. При реконнекте отмена RPC убивает worker чата навсегда

**Воспроизведено:** `app/max_client.py:184–196, 258–287, 364–370`.

При обрыве всем pending futures вызывается `cancel()`. Если worker ждёт такой RPC, `CancelledError` проходит через callback и не ловится `except Exception`. Worker завершается. Очередь остаётся в `_msg_queues`; `_enqueue_message()` создаёт worker только при отсутствии очереди, поэтому следующие сообщения накапливаются без обработки.

Это реально достижимо, например, при `resolve_user()` или скачивании нового аудио через opcode 88. То же отменённое RPC может прервать Telegram handler и не оставить пользователю сообщения об ошибке.

**Исправление:** pending завершать исключением `ConnectionLost`, не отменой вызывающего task. Настоящий `CancelledError` оставить для управляемого shutdown. Worker должен иметь supervisor, восстановление и явную политику возврата текущего сообщения в журнал. На enqueue проверять жизнеспособность worker, но не подменять этим durable-доставку.

### R02 — P1. Гонка регистрации ожидаемого RPC-ответа

**Воспроизведено:** `app/max_client.py:167–196`.

Future регистрируется после `await _send()`. При yield внутри `send_str()` read-loop может обработать быстрый ответ раньше регистрации; он потеряется и запрос завершится timeout. Mock воспроизводит именно это межкорутинное чередование; это не утверждение, что каждый send_str обязательно отдаёт управление.

**Исправление:** выделять seq и регистрировать future до сетевого await; при провале send удалять future в `finally`. Корреляция должна учитывать поколение соединения и ожидаемый opcode.

### R03 — P1. Команды без готового соединения не отклоняются корректно

**По коду:** `app/max_client.py:167–196, 325–345, 392–405`.

При закрытом WS `_send()` возвращает `-1`; разные команды пишут в один `_pending[-1]` и ждут timeout, хотя запрос даже не ушёл. Нет состояния authenticated/ready: Telegram polling запускается раньше MAX, а `_ws` назначается до handshake/auth. При реконнекте seq сбрасывается; запоздалый `finally` старого запроса может удалить pending нового с тем же seq, если выполнение соответствующим образом чередуется.

**Исправление:** state machine `disconnected → connecting → authenticating → ready`; fail-fast или durable-очередь до ready. Не использовать `-1` как ключ RPC. Pending привязывать к connection generation; удалять только собственную future. Проверять соответствие opcode ожидаемому запросу.

### R04 — P1. Авторизация может зависнуть навсегда

**По коду:** `app/max_client.py:334–353, 413–444`.

Handshake/auth отправляются через `_send()`, без deadline. Незапрошенные через `cmd()` ответы `cmd=3` на auth не имеют отдельной обработки и не попадают в обычную ветку событий. Живой WS с ответами на heartbeat ещё не означает успешную авторизацию.

**Исправление:** отдельные deadlines connect/handshake/auth, явная обработка отказа и LOGOUT, диагностика «токен недействителен/авторизация не завершена». Не выдавать транспортную живость за готовность доставки.

### R05 — P1. Watchdog не покрывает важные режимы зависания

**По коду:** `app/max_client.py:198–254, 325–327, 487–491`.

- Пока не получен первый opcode 1, watchdog выключен навсегда; half-open до первого ответа не обнаруживается этим механизмом.
- Исключение при heartbeat только завершает heartbeat-loop, но не закрывает WS.
- `_send()` heartbeat выполняется до проверки silence и не имеет собственного deadline: при зависшей записи проверка может не состояться.
- Счётчик ping replies увеличивается для opcode 1 без строгой проверки `cmd`, seq и успешности ответа.
- Любой входящий кадр продлевает liveness; это не проверка работоспособности авторизации/подписки на сообщения.

**Исправление:** независимый supervisor; timeout записи; принудительное закрытие при сбое heartbeat; проверенная стратегия ping/pong (протокольная или WebSocket-level) и отдельная auth/readiness-проверка. Настроить и протестировать close timeout.

### R06 — P1. Неограниченные очереди и отсутствие надзора за workers

**По коду:** `app/max_client.py:143–144, 258–292`.

`asyncio.Queue()` не ограничена; отдельный вечный worker остаётся на каждый когда-либо встреченный чат. Нет idle cleanup, лимита общей нагрузки и deadline обработки сообщения. `SLOW_MESSAGE_SEC` проверяется только после завершения — зависший callback не даст даже этого предупреждения.

**Исправление:** bounded in-memory очередь поверх durable inbox, лимиты параллельных скачиваний/отправок, idle cleanup, метрики возраста самого старого сообщения и supervisor. Нельзя просто блокировать WS reader на заполненной очереди: тогда перестанут читаться RPC-ответы. Для строгого порядка отдельно определить, блокирует ли failed-сообщение свой чат или помещается в DLQ с видимым пропуском.

### R07 — P1. Устойчивого catch-up после offline нет

**По коду:** `app/max_client.py:316–379, 418–420`; `app/resolver.py:66–118`.

Нет сохранённого cursor/watermark, загрузки истории или сверки пропущенного интервала. Snapshot используется для метаданных. Надёжность после простоя полностью зависит от недокументированного server replay. Нельзя заключать, что reconnect гарантированно доставляет всё накопившееся.

**Исправление:** исследовать history/sync/ack MAX и реализовать возобновление с durable cursor. До этого явно указывать ограничение и измерять разрывы последовательности, если протокол предоставляет подходящие поля.

### R08 — P1. Shutdown не завершает и не сохраняет работу

**По коду:** `app/main.py:86–117, 120–132`; `app/max_client.py:364–370`; `app/max_listener.py:89, 531`.

Нет обработчика SIGTERM для остановки Docker/systemd, `MaxClient.stop()`, join очередей, flush альбомов и ожидания фоновых задач. `KeyboardInterrupt` при ручном `run_until_complete()` не гарантирует выполнение `finally` ещё ожидающего main task. Loop закрывается с незавершёнными tasks. Ошибка при старте sender/application до блока `try` также обходит cleanup.

**Исправление:** `asyncio.run()` с управляемой остановкой по сигналам; startup под `AsyncExitStack`/`try/finally`; реестр задач; прекратить ingress, сохранить незавершённое, ограниченно дождаться отправок, закрыть клиентов. Таймаут остановки контейнера согласовать с grace period. Даже graceful shutdown не заменяет устойчивость к SIGKILL/OOM.

### R09 — P1. `_SyncExecutor` блокирует event loop на DNS

**По коду:** `app/main.py:22–43`.

Любой `run_in_executor(None, ...)` выполняется синхронно. DNS может занимать не несколько миллисекунд, а секунды/десятки секунд при проблемах сети. В этот момент останавливаются оба транспорта, heartbeat, таймеры альбомов и обработка updates.

**Исправление:** обычный ограниченный ThreadPoolExecutor или асинхронный resolver; исправить лимиты процесса/контейнера, а не отключать конкурентность глобально. Добавить event-loop lag metric и тест с медленным resolver.

### R10 — P2. Уведомления об обрыве тормозят реконнект и теряют смысл

**По коду:** `app/max_client.py:372–379`; `app/max_listener.py:443–485`.

Reconnect ждёт `send_status()`, включая Telegram retry и RetryAfter. Проблема Telegram тем самым продлевает недоступность MAX. Throttle не сбрасывается после восстановления: через несколько отдельных аварий новые предупреждения могут подавляться на сутки. Длительная тишина без закрытия WS вообще не вызывает disconnect callback. Используется wall clock, счётчик повышается до подтверждения доставки; успешные reconnect-уведомления не ограничены аналогичным образом.

**Исправление:** отдельная неблокирующая очередь статусов, состояние инцидента, monotonic clock, согласованный throttle loss/recovery и отдельный alert о неготовой авторизации/застрявшей доставке.

### R11 — P2. Upload futures очищаются не во всех ветках

**По коду:** `app/max_client.py:478–485, 695–746`.

`_file_pending` не завершается при disconnect. При отмене upload во время POST/ожидания нет общего `finally`, запись может остаться. Обработка подтверждения после обрыва не гарантирована; положительный смысл payload `UPLOAD_READY` не проверяется.

**Исправление:** cleanup в `finally`, connection generation, явный статус обработки, завершение future при disconnect и recovery-policy для принятого сервером файла.

### R12 — P2. Некорректный кадр может сорвать всё соединение

**По коду:** `app/max_client.py:351–353, 383–387, 480–482, 812–825`; `app/resolver.py:66–118, 180–190`.

JSON не-object, `payload: null`, нечисловой fileId, `text: null`, неожиданные структуры participants/names и вложений не нормализуются системно. Ошибка в `_handle()` приводит к общему reconnect; ошибка после раннего дедупа — к потере сообщения. Типы chat/user IDs также используются непоследовательно.

**Исправление:** валидируемые модели входных событий, нормализация IDs и optional-полей, ограничение размеров, карантин некорректных событий. Разделить ошибку отдельного события и фатальную ошибку протокола. Не выполнять бесконечные reconnect на одном poison-event.

### R13 — P2. Фиксированный reconnect и зависимость старых задач от нового WS

**По коду:** `app/max_client.py:98, 378–379, 430–444`.

Нет exponential backoff/jitter и отдельной политики постоянной auth-ошибки. `_ready_task` отменяется только при следующем snapshot, а не в момент disconnect, и не awaited. Старые callbacks/отправки могут пережить транспорт и обращаться к новому WS без проверки поколения.

**Исправление:** ограниченный backoff с jitter, сброс после устойчивой работы, управляемый lifecycle ready-task и разделение долговечных delivery jobs от connection-scoped RPC.

## 5. Альбомы, порядок и сохранность содержимого

### M01 — P1. FIFO worker не гарантирует порядок конечных отправок

**Воспроизведена гонка таймера; остальные условия следуют из кода:** `app/max_listener.py:52–122, 539–540, 569–572`.

Альбом отправляется самостоятельной timer-task, bucket удаляется **до** окончания send. Последующий `flush()` не находит его и позволяет тексту обогнать медленную отправку. Ещё один сценарий: фото пользователя A буферизуется по `(chat,A)`, текст B вызывает flush только `(chat,B)` и проходит раньше фото A. Пока старый альбом отправляется, новый bucket того же ключа тоже может отправляться конкурентно.

**Исправление:** все конечные отправки одного MAX-чата, включая альбомы, выполнять одним scheduler/worker. Таймер только делает batch готовым, но не отправляет самостоятельно. Учитывать in-flight batch и границы смены отправителя.

### M02 — P2. Подпись ломает объединение фотографий

**Воспроизведено:** `app/max_listener.py:56–65, 205–226`.

Первое фото получает `header + body`, второе — непустой `header`. Buffer считает это конфликтом подписей и flush-ит первое фото. В результате обычное сообщение из двух фотографий с подписью превращается в два отдельных поста. Тест буфера с пустой подписью второго элемента этот путь не покрывает.

**Исправление:** отделить sender/header metadata от пользовательской подписи; собирать run вложений одним batch либо передавать явный флаг продолжения сообщения. Проверять связку listener+buffer+sender, а не только каждый helper отдельно.

### M03 — P1. Последний элемент альбома 11/21/31… теряется

**Воспроизведена форма API-запроса:** `app/tg_sender.py:205–238`.

Специальный случай одного элемента предусмотрен только для всего списка. Список из 11 элементов разбивается на 10 и 1; последняя часть отправляется через `send_media_group`, где требуется минимум 2 элемента. Реального вызова Telegram в проверке не было; сформированный одноэлементный запрос подтверждён mock-проверкой.

**Исправление:** обрабатывать chunk длиной 1 через send_photo/send_video либо балансировать части 9+2. Хранить результат каждой части и прекращать/откладывать последовательность при провале.

### M04 — P2. Эвристика альбомов объединяет независимые сообщения

**По коду:** `app/max_listener.py:17–22, 34–41, 85–89, 125–150`.

Группировка по отправителю и времени не различает два самостоятельных фото и настоящий альбом. Окно начинается после скачивания: большие/медленные части одного альбома могут разъехаться. Объявленные 15 секунд ограничивают ожидание bucket после первого add, а не время от поступления сообщения и не полную доставку.

**Исправление:** использовать подтверждённый group/album ID, если доступен; иначе документировать эвристику, группировать прежде скачивания, ограничивать размер batch и учитывать границы сообщений. Не делать задержку batching основанием для нарушения порядка.

### M05 — P1. Вложения самого reply/forward-сообщения игнорируются

**По коду:** `app/max_listener.py:371–422, 545–553`.

Ветка link обрабатывает вложенный оригинал и `msg.text`, затем делает return. `msg.attaches` нового сообщения не обрабатываются. Reply с собственной фотографией может потерять фото. Повторная пересылка медиа оригинала для каждого reply также расходует трафик и создаёт визуальные дубли. Для audio во вложенном сообщении передаётся контекст внешнего `msg`, что может дать неверные chat/message IDs download RPC.

**Исправление:** отдельно моделировать цитируемый объект и новое содержимое; доставлять собственные attaches всегда. При наличии mapping использовать Telegram reply_to_message_id; для пересланного download брать исходные идентификаторы.

### M06 — P1. Текст помечается использованным, хотя не был доставлен

**По коду:** `app/max_listener.py:207–228, 273–277, 324–330`.

Результат `_send_attach()` игнорируется, `text_used` становится True просто из-за наличия body. PHOTO без URL возвращает False, но текст уже не отправляется отдельно. Стикер при успешной отправке не несёт caption, однако body также считается использованным. Скрытые ошибки Telegram усиливают этот дефект.

**Исправление:** явный результат `{attachment_delivered, caption_delivered, destination_ids}`. Текст считать доставленным только по подтверждённому результату; поддержать отдельную отправку подписи для типов без caption.

### M07 — P1. Сырые HTML-строки обрезаются с потерей текста и валидности

**По коду:** `app/tg_sender.py:109–112, 133–138`.

Обрезание может попасть внутрь `&amp;` или тега, оставив невалидный HTML. Telegram отвергнет весь запрос, retries повторят ту же ошибку. Кроме того, `len()` escaped HTML не равно длине отображаемого текста. Длинные сообщения и подписи безвозвратно усекаются.

**Исправление:** разделять текст с entities на валидные части по правилам Bot API; длинную подпись переносить в дополнительные сообщения. Не резать markup/Unicode-последовательности произвольно. Для intro/profile также учитывать лимиты подписи и текста.

### M08 — P1. Неограниченная загрузка медиа в память

**По коду:** `app/max_client.py:786–807`; `app/max_listener.py:85, 125–150`; `app/tg_handler.py:174–178`.

Файл полностью читается через `resp.read()`, затем может долго храниться в album bucket; много чатов качают параллельно. Нет лимита bytes на файл/bucket/процесс, контроля Content-Length и фактического потока. Это может завершить процесс по OOM, потеряв все очереди.

**Исправление:** streaming во временный spool с жёсткими лимитами фактически прочитанных байт, bounded concurrency, квоты диска и cleanup. Проверять известный размер Telegram до getFile/download; oversized media отражать понятным сообщением. Лимиты download из TG и upload в TG — разные, их нельзя сводить к одной цифре 20 МБ.

### M09 — P2. Скачивание и выбор медиа дают лишние ошибки и деградацию

**По коду:** `app/max_listener.py:125–150, 164–185, 273–320`; `app/max_client.py:597–670`.

- Неудачный download groupable-фото повторяется в `_send_attach()`: до двух полных ожиданий по 120 секунд без осмысленного backoff.
- PHOTO не использует `baseRawUrl`/photoToken-only варианты; FILE без url не пробует известный opcode 88; VIDEO всегда ограничен preview, хотя проект знает об opcode 83.
- `.gif`, `.bmp`, `.avi`, `.mkv`, `.webm` классифицируются только по расширению, без проверки формата/ограничений Telegram и fallback в document при неподдерживаемом медиа.
- `_probe_audio_url()` описан как HEAD, но делает GET; принимает любой 200 с Content-Type, отличным от HTML, включая JSON/изображение. Последующее переименование bytes в `.ogg`/`.m4a` не превращает их в аудио.
- Четыре последовательных экспериментальных audio URL могут задержать чат до ~60 секунд ещё до download/RPC; capability cache отсутствует.

**Исправление:** единый результат download и классификация ошибок; проверка MIME/signature, корректный fallback в document; проверенные download RPC; экспериментальный probing убрать из обычной обработки или изолировать флагом и кешем возможностей. Недоступность медиа показывать явно, не считать placeholder эквивалентом доставки оригинала.

### M10 — P2. Геолокация с нулевой координатой теряется

**По коду:** `app/max_listener.py:348–355`.

`or` и `if lat and lon` отбрасывают корректные 0 широты/долготы. Нет проверки диапазона и типов.

**Исправление:** проверять `is not None`, нормализовать числа, валидировать диапазоны; по возможности использовать нативный send_location.

### M11 — P2. Форматирование MAX→TG не реализовано; ряд TG-событий игнорируется

**По коду:** `app/max_client.py:82–92, 817–825`; `app/max_listener.py:571–572`; `app/tg_handler.py:115, 923–926`.

MAX `elements` не переносятся в модель/рендеринг, текст просто HTML-escaped. В TG→MAX нет обработки stickers, animations, video notes, contacts, locations; edited_message игнорируется, потому что handlers читают `update.message`. Альбомы TG отправляются по одному файлу, TG reply-связь не переносится в MAX.

**Предложение:** составить честную матрицу поддерживаемых типов и направлений, показывать отказ для неподдерживаемого исходящего содержимого. Форматирование и reply/edit добавить через общий message mapping. Различать намеренные ограничения и молчаливую потерю.

## 6. TopicStore, маршрутизация и команды

### T01 — P1. Повреждение карты приводит к тихому созданию новой карты

**По коду:** `app/topics.py:31–46`.

Любая ошибка чтения/структуры приводит к пустому состоянию. При следующем создании топика исходный файл может быть заменён новой урезанной картой. Нет backup, проверки схемы и режима восстановления. Тест `test_corrupt_file_starts_empty` закрепляет именно опасное поведение.

**Исправление:** fail-closed для изменяющих операций, сохранить повреждённый файл, загрузить проверенный backup или потребовать восстановления; read-only диагностика. Проверять структуру, типы, уникальность topic IDs и принадлежность целевому аккаунту/супергруппе.

### T02 — P1. Успех в памяти не означает сохранение на диск

**По коду:** `app/topics.py:48–59, 71–80, 85–94`.

Состояние меняется раньше `_save()`, часть исключений записи подавляется. При disk-full/ошибке replace процесс сообщает об успешной привязке, но после рестарта она исчезает. `makedirs()`/`mkstemp()` находятся вне try и, наоборот, могут пробросить исключение. Atomic replace защищает от частично записанного JSON, но без fsync файла/каталога не гарантирует сохранность при аварии питания.

**Исправление:** транзакционная запись с propagation ошибки; менять опубликованное состояние после успешного сохранения; fsync по требуемой гарантии, backup. Для журнала доставки и mapping рациональнее SQLite с транзакциями и явно выбранным synchronous-режимом.

### T03 — P1. Нарушается взаимная однозначность прямой и обратной карты

**Воспроизведён stale reverse mapping:** `app/topics.py:71–74`.

Повторный `set_topic(chat, new_topic)` не удаляет старый `_by_topic[old_topic]`: оба топика продолжают отправлять в один MAX-чат. Присвоение уже занятого topic другому чату также оставляет противоречащую прямую карту. Состояние может отличаться до и после reload.

**Исправление:** enforce unique constraints в обе стороны, атомарное remap и удаление устаревших индексов; тесты replacement, collision, remove-after-remap и reload.

### T04 — P1. `/bind` и `/add` обходят блокировку создания топиков

**По коду:** `app/tg_sender.py:86–105`; `app/tg_handler.py:413–445, 558–595`.

MAX worker и Telegram command могут одновременно проверить отсутствие связи и создать два топика. Глобальный lock sender не используется командами. Создание в Telegram и запись mapping не атомарны: crash между ними оставляет orphan-topic даже при одном процессе.

**Исправление:** единый TopicService с per-chat lock для всех путей, durable creation intent и recovery. Два экземпляра процесса с одним state не поддерживаются: нужен instance lock/leader election, иначе JSON last-writer-wins и дубли отправок/топиков.

### T05 — P1. Удаление топика не синхронизировано с очередью и текущей привязкой

**По коду:** `app/tg_handler.py:677–725`; `app/max_listener.py:524–540`.

Callback доверяет данным кнопки, не сверяет `query.message.chat.id`, актуальную пару chat↔thread и ревизию операции. Mapping удаляется до результата Telegram. Повтор старой кнопки после новой привязки может удалить новую запись, пытаясь удалить старый thread. Параллельный входящий worker/album продолжит слать в старый топик либо создаст новый во время удаления.

**Исправление:** authorization + проверка супергруппы + compare-and-delete текущей связи; одноразовая операция с revision/TTL; общий lock с create/forward, состояние deleting и reconciliation при неизвестном результате API. Политику «снять связь даже при провале удаления» сделать явной.

### T06 — P1. Удалённый/закрытый топик не восстанавливается; create failure смешивает чаты

**По коду:** `app/tg_sender.py:62–105, 124–129`; `app/max_listener.py:524–525`.

Existing thread считается валидным без обработки topic-not-found/closed при отправке. Такие ошибки ретраятся как обычные, затем скрываются. При create failure отправка идёт в General с `thread_id=None`: теряется изоляция чатов и возможность ответа по mapping; сообщения могут оказаться в неожиданном месте.

**Исправление:** классифицировать ошибки Telegram, валидировать/reconcile mapping, ставить сообщение в retry при невозможности корректной маршрутизации. General fallback — только как явно выбранная политика с заметным предупреждением.

### T07 — P2. Метаданные и названия топиков застревают в неправильном состоянии

**По коду:** `app/max_client.py:418`; `app/resolver.py:66–118`; `app/max_listener.py:509–522`; `app/tg_sender.py:21–24, 74–84`.

Snapshot запрашивает 10 чатов, пагинации и CHAT_GET для неизвестного чата нет. Новый DM/группа может быть неправильно классифицирован, группа названа именем первого отправителя. Переименование разрешено только для placeholder; имя отправителя уже считается нормальным и не заменится названием группы. Отрицательный числовой title не распознаётся через `isdigit()`.

**Исправление:** on-demand CHAT_GET, пагинация/capability-aware snapshot, TTL метаданных, источник title (`manual`, `placeholder`, `resolved`) вместо эвристики строки. Пользовательское название сохранять, автоматически вычисленное — обновлять.

### T08 — P2. Profile/intro fetch не обновляет кеш; в production остался опасный probing

**По коду:** `app/tg_handler.py:291–297, 575–579, 803–829`; `app/resolver.py:131–172`.

`max_client.fetch_contacts()` возвращает dict, но сам не заполняет resolver. В intro/add ответ выбрасывается, после чего перечитывается прежний кеш. Single-contact ответ в resolver может заполнить `users`, но не `contacts_raw`: `_deep_extract()` не добавит raw, если имя уже есть. `/intro` не обновляет уже закешированный аватар, вопреки обещанному сценарию refresh.

В `/profile` сохранён перебор непроверенных payload/opcodes 33/36 и вариантов CONTACT_GET. По известным особенностям протокола некорректный запрос способен закрыть общий WS. Пользовательская команда не должна исследовать протокол на боевом соединении.

**Исправление:** публичный `resolver.fetch_contact(force_refresh=...)`, обязательный разбор ответа во всех формах; убрать probing из production, оставить отдельный исследовательский инструмент с явным запуском.

### T09 — P2. Кеш ошибок контактов вечный, успешные метаданные не обновляются

**По коду:** `app/resolver.py:22, 38–62, 122–172`.

Один transient failure добавляет user ID в `_fetch_failed` до рестарта. Параллельные чаты могут делать одинаковые lookup одновременно, нет single-flight. Кеши не ограничены и не имеют TTL; deep-extraction может принять произвольный name-bearing dict с ID за контакт.

**Исправление:** короткий negative TTL, bounded positive TTL, сброс временных ошибок при восстановлении, single-flight и строгие схемы контактов. Batch делить по известным лимитам сервера.

## 7. Telegram ingress, безопасность и данные

### S01 — P1. При запуске удаляются накопившиеся Telegram updates

**По коду:** `app/main.py:100–103`.

`drop_pending_updates=True` намеренно удаляет сообщения, отправленные владельцем во время простоя. Отдельно нет durable журнала updates: polling может уже получить/подтвердить их, а процесс упасть до завершения MAX-send.

**Исправление:** отключить drop по умолчанию, хранить входящие `(bot_id, update_id)`/`(chat_id, message_id)` и статусы исходящих операций; явно согласовать политику старых updates. Простое отключение drop не решает crash-window после получения update.

### S02 — P2. Один медленный upload блокирует все Telegram команды

**По коду:** `app/tg_handler.py:184–272, 899–906`.

Application использует стандартную последовательную обработку updates, а handler выполняет download/upload/ожидание UPLOAD_READY целиком. Долгое видео блокирует ответы и команды в других топиках. Ошибки uploader вне try вокруг `send_message` уходят в общий PTB logging; собственного error handler нет.

**Исправление:** быстрый ingress в durable per-chat outbox, независимые chat workers и global limits. Простое включение `concurrent_updates=True` нарушит порядок и усилит гонки mapping; его одного недостаточно. Добавить error handler и явное уведомление о состоянии операции.

### S03 — P1. Авторизация permissive и не fail-closed

**По коду:** `app/tg_handler.py:125–127, 392–394, 499–501, 683–685, 919`; `.env.example:16–18`.

Без `TG_ALLOWED_USER_ID` любой участник супергруппы может отправлять от имени MAX-аккаунта и выполнять управляющие команды. Это задокументировано, но опасно для общей группы. Даже при ограничении условие пропускает событие с `effective_user is None`. Значение allowed ID `0` трактуется как отсутствие ограничения. CallbackHandler не ограничен chat_filter; актуальная принадлежность кнопки группе отдельно не проверяется.

**Исправление:** fail-closed проверка пользователя и супергруппы в общей функции; запрещать sender_chat/анонимные действия, если не предусмотрены явно; валидировать положительный user ID. Разделить права отправки и управления топиками. Для персонального режима сделать allowlist обязательным либо явный выбор режима «вся группа».

### S04 — P1. Логи раскрывают MAX-токен и содержимое переписки

**По коду:** `app/max_client.py:179–180, 415–422, 593–595, 624, 640–664, 800–804`; `app/max_listener.py:465–468, 495–502`; `app/main.py:50–72`.

При `LOG_LEVEL=DEBUG` исходящий AUTH пакет содержит `token` в `raw[:800]`; отдельный `DEBUG=true` не требуется. INFO логирует фрагменты сообщений, имена, contact/open-link ответы и подписанные media URLs. Debug snapshot также содержит персональные данные. Ротация ограничивает объём, но не устраняет раскрытие.

**Исправление:** централизованная redaction до сериализации логов; никогда не логировать auth payload, токены и query секреты; по умолчанию IDs/тип/размер/latency вместо текста и полных URL. Ограничить доступ и срок хранения логов/debug. Если DEBUG уже использовался в реальной среде, проверить обращение с существующими логами и необходимость обновления токена без копирования секретов в отчёт.

### S05 — P1. HTTP-загрузчик не ограничивает назначения запросов

**Условный риск:** `app/max_client.py:748–807`; `app/max_listener.py:164–174, 285–325`; `app/tg_handler.py:316–346`.

URL из протокольных объектов передаётся aiohttp без проверки host, private/loopback/link-local IP и редиректов. Если атакующий способен влиять на attachment/avatar URL, возможен SSRF и пересылка доступного HTTP-содержимого в Telegram. Способность обычного пользователя MAX задать произвольный URL в этих полях аудитом не доказана.

**Исправление:** разрешённые HTTPS CDN hosts, проверка DNS/IP и каждого redirect, лимит bytes; отдельная политика для download/upload. Не полагаться на `startswith("http")`. `/add` также проверять через URL parser и точный host: проверка подстроки `max.ru/` принимает посторонние домены/пути, хотя сама ссылка затем передаётся MAX, а не скачивается мостом напрямую.

### S06 — P2. `MAX_CHAT_IDS` фильтрует только входящие MAX-события

**По коду:** `app/max_client.py:147–149, 455`; `app/tg_handler.py:112–129, 380–445`.

Ручной bind и отправка из Telegram не проверяют этот список. Если список предполагается как граница доступа, можно получить односторонний чат: отправка разрешена, ответы отфильтрованы.

**Исправление:** назвать настройку inbound_filter либо применять единый allowlist обеим сторонам и командам; проверять доступность MAX-чата при bind. В документации различить маршрутизационный фильтр и permission boundary.

## 8. Конфигурация, сборка и эксплуатация

### O01 — P1. Docker переносит бинарные зависимости glibc → musl

**По Dockerfile, сборка не выполнялась:** `Dockerfile:1–14`.

Зависимости устанавливаются в `python:3.12-slim` и копируются в `python:3.12-alpine`. У aiohttp и транзитивных пакетов есть native extensions; manylinux/glibc wheels не совместимы с musl автоматически. Наличие Python fallback у части пакетов может скрыть проблему или снизить производительность, но не делает схему корректной. Утверждение CLAUDE.md о совместимости слоёв не является гарантией ABI.

**Исправление:** одинаковая базовая libc/семейство образов на build/runtime stages; лучше один slim для начала. CI должен собирать образ и запускать imports/smoke-test внутри него. Проверять обе архитектуры, если используются amd64/arm64.

### O02 — P2. Невоспроизводимые зависимости и заявленная совместимость

**По коду:** `requirements.txt`; `app/tg_handler.py:903–905`.

Все зависимости имеют только нижнюю границу; новый build может получить несовместимые версии. Ветка proxy использует API, которое следует проверить на заявленном минимуме PTB 21.0, а не только на установленном 22.8. Нет lock/hashes, dev requirements и матрицы Python/PTB. Текущий `pip check` проверяет metadata compatibility, но не runtime API и не CVE.

**Исправление:** lock проверенного набора, отдельные dev dependencies, автоматическое плановое обновление с CI. Согласовать диапазон PTB с реально используемым builder API; при поддержке `RetryAfter.retry_after` как timedelta нормализовать его перед `asyncio.sleep`.

### O03 — P2. Контейнер жив не означает, что мост работает

**По коду:** `docker-compose.yml`; `app/main.py:74–117`.

Нет health/readiness-check, проверки forum/admin permissions при старте, метрик авторизации/доставки и внешнего контроля. `restart: unless-stopped` помогает при выходе процесса, но не при мёртвом worker или вечном ожидании auth. Даже добавленный healthcheck сам по себе не заставляет обычный Compose перезапускать unhealthy-контейнер.

**Исправление:** readiness по auth + жизнеспособности workers/очередей; liveness по event-loop/supervisor; alerts по backlog age и errors; startup preflight Telegram. Отдельно настроить механизм реакции на unhealthy, без рестарт-шторма на кратком сбое внешней сети.

### O04 — P2. Нет ограничений ресурсов и политики сохранения состояния

**По коду:** `docker-compose.yml:4–16`; `Dockerfile:16–18`.

Контейнер работает под root, нет memory/CPU/pids ограничений, read-only rootfs, backup state и stop grace configuration. Значение nproc 65535 не решает причину проблем создания потоков. Логи приложения дублируются в stdout; ротация Docker logs зависит от настроек daemon и здесь не задана. `MALLOC_ARENA_MAX` установлен только в builder и не наследуется независимым runtime stage.

**Исправление:** непривилегированный UID с доступом к state/log/spool, разумные квоты и наблюдение, log rotation для контейнера, backup/restore rehearsal, документированная single-instance модель. При лимитах памяти сначала исправить unbounded queues/downloads, иначе OOM станет чаще.

### O05 — P2. Настройки валидируются неполно и слишком поздно

**По коду:** `app/config.py:23–74`; `app/max_client.py:147–149`; `app/main.py:80–91`.

MAX_CHAT_IDS парсится уже после запуска TelegramSender; malformed значение вызывает необработанный ValueError и обходит startup cleanup. Обязательные значения из пробелов принимаются; boolean-значения с пробелами не распознаются; ошибочный LOG_LEVEL молча становится INFO. Не проверяются положительный allowed user ID, формат proxy, пригодность state/log directories и идентичность state выбранному аккаунту/группе.

**Исправление:** полная нормализация/валидация settings до открытия клиентов, понятные ошибки, проверка прав на state/spool; manifest состояния с account/group IDs и schema version. При смене TG_CHAT_ID старые thread IDs не должны молча использоваться в новой группе.

## 9. Что уже сделано правильно

- Per-chat FIFO существенно лучше независимых tasks для каждого DISPATCH; исправлять нужно разрыв между callback и фактической отправкой.
- `on_ready` вынесен из read-loop, что устраняет deadlock RPC при резолвинге контактов.
- `_file_pending` регистрируется до HTTP POST, учитывая ранний UPLOAD_READY.
- Mutable chat filter теперь изолирован на экземпляр.
- Incoming текст и имена обычно HTML-escaped.
- TopicStore использует tempfile + os.replace; это полезная основа атомарности файла.
- Есть bounded seen-cache, базовый watchdog, rate-limit retries и ротация файловых логов.
- Статус в личку при ошибке не перенаправляется в общую группу.
- Тесты фиксируют несколько исторических регрессий; базовый набор полностью проходит.

Эти механизмы стоит сохранить, но связать общей моделью подтверждения и восстановления доставки.

## 10. Предлагаемая целевая архитектура

### 10.1. Хранилище

Для текущего масштаба достаточно SQLite на существующем state volume:

- `accounts` / manifest: MAX account ID, bot/group ID, schema version.
- `inbox`: source, account, chat, message ID, revision/hash, payload, received_at; UNIQUE по корректному ключу события.
- `deliveries`: logical message, destination, status, attempts, next_retry_at, last_error, connection-independent operation ID.
- `delivery_parts`: часть текста/медиа, Telegram message IDs или MAX message ID/cid, состояние confirmed/uncertain.
- `topics`: уникальные пары chat↔thread, происхождение title, lifecycle/revision.
- `cursors`: подтверждённые source sync positions, если протокол предоставляет такую возможность.

Бинарные данные хранить в ограниченном spool, не в неограниченных Python bytes. После crash возвращать processing-jobs в recovery, а не автоматически отправлять всё заново: сначала учитывать confirmed/uncertain parts.

### 10.2. Pipeline

```text
MAX WS reader / Telegram update ingress
  → validate + normalize
  → durable inbox / outbox transaction
  → per-chat scheduler
  → enrich metadata + prepare media
  → sequential destination sender
  → persist confirmed destination IDs / failure / uncertain
```

WS reader не ждёт Telegram, download и длинных callbacks. Он должен оставаться доступным для RPC-ответов. Альбом — планируемая группа delivery-parts, а не отдельная неучтённая timer-task. Глобальные семафоры ограничивают HTTP/Telegram concurrency; один медленный чат не останавливает остальные.

### 10.3. Политика ошибок

| Ситуация | Действие |
|---|---|
| Явный transient failure до принятия | Retry с backoff/jitter |
| Telegram 429 | Общий cooldown подходящей области, без параллельного retry-шторма |
| Невалидный HTML/тип медиа | Исправить представление/fallback, не повторять тот же запрос трижды |
| Topic not found/closed | Reconcile mapping по выбранной политике |
| Forbidden/потеря прав | Pause destination + alert |
| Timeout после потенциального принятия | `uncertain`, сверка/явная политика повторов |
| Некорректный входной payload | Карантин + метрика, без обрыва всего моста |
| Отказ авторизации MAX | Readiness false + понятный alert, ограниченный backoff |

Технический retry не должен скрывать постоянную ошибку. Необходимо определить пользовательскую политику для DLQ и порядка после failed-сообщения.

### 10.4. Эксплуатационные дополнения

- `/status`: auth state, last_rx, oldest queued age, failed/uncertain count.
- `/retry` или административный инструмент для failed delivery с учётом частичных результатов.
- Диагностический экспорт без токенов и текста переписки по умолчанию.
- Метрики: delivered/failed/uncertain, dedup replay/edit, queue age/size, worker count, reconnect reasons, event-loop lag, HTTP bytes/latency.
- Backup/restore state и проверка восстановления на отдельной тестовой конфигурации.
- Capability registry экспериментального MAX-протокола вместо probing в пользовательских командах.

## 11. Проверки и пробелы тестирования

### Подтверждено изолированными проверками

| Проверка | Наблюдение |
|---|---|
| Два чата, один message ID | Второй помечается duplicate |
| JSON `id: null` | ID превращается в `"None"` |
| Ответ RPC внутри await отправки, до регистрации future | Ответ теряется, cmd возвращает `{}` по timeout |

Штатные тесты проверяют в основном helpers, defaults, happy-path routing и отдельные регрессии. Число тестов не равно покрытию отказоустойчивости. ### Необходимые regression/integration тесты

1. Failure после принятия, до отправки: replay не теряется и не создаёт вторую активную job.
2. Crash до send, после server acceptance, после response, до commit: корректные pending/confirmed/uncertain состояния.
3. Backlog больше dedup limit и повтор ещё не отправленного сообщения.
4. Cross-chat ID, null/missing ID, edit с тем же ID, строковые/числовые IDs.
5. Локальный WS test-server: ранний ответ, auth timeout/error, disconnect при cmd/upload, half-open, stalled send, malformed frame, seq generation.
6. Worker после ConnectionLost продолжает/восстанавливается; настоящий shutdown cancellation завершает его управляемо.
7. Album→text от другого автора; timer-send in flight; две фото с подписью; 1/2/10/11/20/21 элементов; failure второй части.
8. Reply с собственными attaches; sticker с body; PHOTO без URL; длинный escaped text/caption; координаты 0.
9. Disk-full, replace failure, corrupted state, remap/collision, create-vs-bind, delete-vs-incoming, старая delete-кнопка, два экземпляра.
10. TG offline updates, slow upload в одном топике и команды в другом, unsupported media, uploader exception.
11. SIGTERM во время download/send/album-buffer, startup failure, restart с pending jobs.
12. Проверка логов на sentinel token: ни INFO, ни DEBUG не должны его содержать.
13. HTTP redirect в private IP, oversized/chunked response, неправильный MIME; никаких запросов к реальной локальной инфраструктуре.

## 13. Критерии готовности надёжного релиза

- Ни одна подтверждённо принятая мостом job не исчезает при временной ошибке или рестарте.
- Сбой RPC не может навсегда остановить один чат.
- У каждого сообщения виден итог: delivered, pending, failed или uncertain; «успех» не означает просто возврат callback.
- Порядок конечных отправок сохраняется согласно документированной политике, включая альбомы и разных авторов.
- Replay и edit различаются; IDs корректно scoped и переживают рестарт.
- Частично доставленный batch не пересылается целиком вслепую.
- Память и spool ограничены, а превышение лимита наблюдаемо и не приводит к молчаливой потере.
- Повреждение state не создаёт новую карту поверх старой без восстановления.
- SIGTERM, auth failure, недоступность Telegram/MAX и disk-full покрыты проверками.
- В логах нет токенов; образ воспроизводимо собирается и проходит smoke-test.

**Итог:** проект имеет полезную рабочую основу, однако следующая итерация должна быть сосредоточена на модели доставки и восстановлении после отказов. Главный выигрыш даст согласованный журнал состояний и единый последовательный путь отправки, а не отдельное увеличение кеша дедупликации или числа retries.

## 14. Контроллер соединения MAX и поддержание сессии

### 14.1. Цель и границы возможностей

Предлагается добавить контроллер, который обнаруживает зависшее подключение, восстанавливает транспорт и авторизацию и проверяет фактическую готовность моста к обработке сообщений. Существующие heartbeat/reconnect — основа, но недостаточная для сценариев R01–R09.

Необходимо различать потерю связи и потерю авторизации:

| Ситуация | Возможность автоматического восстановления |
|---|---|
| Обрыв сети, закрытый или зависший WebSocket | Закрыть старое соединение, подключиться и авторизоваться заново |
| Handshake/auth зависли без ответа | Прервать по deadline, повторить с backoff, сообщить о неготовности |
| WS жив, но worker чата остановился | Восстановить обработчик и незавершённую работу; одного reconnect недостаточно |
| Токен истёк, отозван или заменён | Нужен подтверждённый механизм обновления credentials либо повторная авторизация |

**Причина текущего симптома «сессия протухла» не установлена.** По коду возможны и зависшая авторизация, и half-open соединение, и остановка worker при отмене RPC. Нельзя автоматически считать отсутствие сообщений доказательством истечения токена: в чате может просто не быть новых событий.

Heartbeat поддерживает активность транспорта и помогает обнаруживать обрыв, но **не гарантирует продления срока авторизации**. Повторное подключение с отозванным токеном не восстановит доступ.

### 14.2. Состояния и таймауты

Контроллер должен иметь явную машину состояний:

```text
disconnected → connecting → handshaking → authenticating → ready
       ↑              ошибка/timeout → reconnect_backoff ─┘

Подтверждённый отказ credentials → auth_required
Остановка процесса → stopping → stopped
```

`ready` устанавливается после успешного, валидированного AUTH_SNAPSHOT; открытый сокет сам по себе не означает готовность. Дополнительно состояние доставки должно отражать работоспособность workers и destination, чтобы живой MAX WS не маскировал остановленную пересылку.

Отдельные настраиваемые deadlines нужны для:

- установления соединения;
- handshake;
- авторизации;
- записи в WebSocket;
- ожидания RPC/проверочного ответа;
- закрытия зависшего соединения.

Конкретные значения следует подобрать по измерениям нормальной сети и проверить fault-injection тестами. Авторизационный timeout обозначать как «авторизация не завершилась», а не как доказанный «невалидный токен». Последнее допустимо только при распознанном отказе MAX.

### 14.3. Независимый watchdog

Watchdog должен выполняться независимо от корутины, отправляющей heartbeat. Если запись в сокет зависла, контроллер всё равно обязан обнаружить deadline и начать восстановление.

Контролировать отдельно:

1. Время последнего входящего кадра по monotonic clock.
2. Время и результат последней подтверждённой проверки соединения.
3. Завершение авторизации и текущее поколение соединения.
4. Жизнеспособность read/heartbeat tasks и workers.
5. Возраст очереди, продвижение активных jobs и результаты отправки.

Способ проверки MAX нужно подтвердить на реальном протоколе: opcode heartbeat, WebSocket ping/pong либо безопасный read-only RPC с известным ответом. Нельзя считать неподдерживаемый ping обязательным и получать реконнект каждые несколько минут на здоровом простаивающем соединении. С другой стороны, отсутствие поддержки opcode 1 не должно навсегда отключать весь контроль зависаний, как сейчас.

Ошибка heartbeat должна переводить соединение в восстановление, а не просто завершать heartbeat-task. Фоновые read-mark/event кадры доказывают только транспортную активность и не заменяют проверку авторизации/доставки.

### 14.4. Безопасное восстановление

- Единственный supervisor управляет reconnect, чтобы несколько обнаруживших проблему tasks не открывали параллельные соединения.
- Применять exponential backoff с верхней границей и jitter; сбрасывать задержку после устойчивой работы, а не сразу после открытия WS.
- Присваивать каждому соединению generation ID; ответы и cleanup старого поколения не должны затрагивать новый transport.
- При обрыве завершать connection-scoped RPC исключением `ConnectionLost`. Не вызывать `cancel()` так, чтобы оно уничтожало долговечный worker чата (R01).
- Pending delivery jobs сохранять и восстанавливать через журнал. Операции с неизвестным результатом не отправлять повторно вслепую.
- До `ready` исходящие сообщения помещать в сохраняемую очередь либо явно отклонять по выбранной политике; не создавать ожидания по seq `-1`.
- Статусные уведомления отправлять через независимую очередь: недоступный Telegram не должен задерживать reconnect MAX.
- При shutdown прекращать новые попытки reconnect, сохранять незавершённую работу и ограниченно ожидать закрытия задач/клиентов.

### 14.5. Диагностика и уведомления

Разделить сообщения пользователю и причины в метриках:

- «MAX: сеть недоступна, повторное подключение»;
- «MAX: авторизация не завершилась за отведённое время»;
- «MAX отклонил токен, требуется обновление авторизации» — только при подтверждённом отказе;
- «Обработка чата остановилась/очередь не продвигается»;
- «MAX: соединение и авторизация восстановлены».

В `/status` показывать состояние, длительность текущего инцидента, last_rx/probe age, число reconnect, причину последнего сбоя, backlog age и failed/uncertain jobs. Не выводить токены, auth payload и подписанные media URLs. Уведомления ограничивать на уровне инцидента, а не пожизненного счётчика отключений; внешнее наблюдение нужно на случай одновременной недоступности Telegram.

### 14.6. Автоматическое обновление токена: отдельное исследование

В проекте нет реализованного и подтверждённого refresh-механизма MAX. Чтобы оценить возможность автоматического продления авторизации, необходимо исследовать официальный веб-клиент:

1. Обновляет ли он токен в ходе длительной обычной сессии.
2. Какие запросы или серверные события сопровождают обновление.
3. Передаёт ли AUTH_SNAPSHOT/другой ответ новые credentials и как клиент сохраняет их.
4. Что происходит при повторном входе, logout, отзыве токена и смене устройства.
5. Требуются ли дополнительные cookies/device credentials и допускается ли восстановление без участия владельца.

Исследование проводить отдельно от production-моста, с редактированием секретов в захватах. Непроверенные опкоды не пробовать автоматически на рабочем соединении.

Если refresh поддерживается, реализовать атомарное защищённое сохранение новых credentials, single-flight обновление и согласованную смену авторизации. Заранее определить источник истины между runtime credential store и переменными окружения, чтобы после рестарта не вернулся устаревший токен. Если refresh не предусмотрен, контроллер должен честно перейти в `auth_required`, уведомить владельца и поддерживать понятный сценарий обновления токена.

Не использовать искусственные сообщения или периодический повторный login как способ «не дать сессии протухнуть» без подтверждения поведения MAX: это не гарантирует продления токена и может само менять состояние авторизации.

### 14.7. Порядок реализации и критерии приёмки

**Первый шаг:** исправить R01, добавить state machine, auth deadlines, независимый watchdog и reconnect supervisor. Это закрывает известные причины замирания и даёт диагностику для отличия транспортного сбоя от проблем credentials.

**Второй шаг:** связать контроллер с durable-доставкой, восстановлением workers, graceful shutdown, метриками и `/status`.

**Третий шаг:** после исследования протокола реализовать refresh, если он действительно доступен; иначе отработать сценарий `auth_required` и смены токена владельцем.

Проверки приёмки:

- Обрыв и восстановление сети автоматически возвращают мост в `ready` без ручного рестарта.
- Молчание на handshake/auth и зависшая запись ограничены deadlines.
- Half-open обнаруживается выбранной проверенной стратегией, включая случай до первого heartbeat-ответа.
- Отсутствие сообщений в здоровом простаивающем чате не вызывает reconnect-loop.
- Обрыв во время RPC не уничтожает worker и не теряет pending jobs.
- Рабочий сокет при остановленном worker не отображается как полностью здоровая доставка.
- Подтверждённо отозванный токен вызывает `auth_required`, а не бесконечные быстрые попытки и ложное уведомление о восстановлении.
- Недоступность Telegram не блокирует восстановление MAX.
- Старые connection tasks не воздействуют на новое соединение; SIGTERM прекращает reconnect корректно.
- Если реализован refresh, новые credentials переживают рестарт и не появляются в логах.
