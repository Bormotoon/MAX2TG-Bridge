# MAX2TG-Bridge

> Двусторонний мост между мессенджером **MAX** (`web.max.ru` / `ws-api.oneme.ru`) и **Telegram** через форум-топики в супергруппе.

Каждый чат MAX становится отдельным форум-топиком в твоей супергруппе Telegram. Входящие сообщения приходят в свой топик; ответ, написанный в этом топике, уходит собеседнику в MAX от твоего имени. При создании топика в него постится и закрепляется карточка собеседника.

## Гарантии доставки

Это главное, что стоит понимать про мост, поэтому начнём с него.

Каждое принятое событие попадает в **журнал доставки** (SQLite в `state/`) до того, как мост попытается что-то отправить. Событие считается завершённым только после подтверждения от Telegram (или от MAX для обратного направления). Из этого следует:

- **Сбой не теряет сообщение.** Упал процесс, отвалилась сеть, Telegram ответил 5xx — задача остаётся в журнале и будет повторена с экспоненциальной паузой.
- **Повтор не создаёт дубль.** Дедупликация — это уникальный ключ `(источник, аккаунт, чат, message_id, ревизия)` в базе, а не кеш в памяти. Он не может «забыть» недоставленное сообщение и переживает рестарт.
- **Порядок сохраняется.** На каждый чат — один воркер, который сам решает, что объединить в альбом, сам это отправляет и только потом записывает результат. Ничего не отправляется фоновой задачей в обход очереди.
- **Частично доставленное не пересылается целиком.** Если из 11 фото ушли 6, повтор отправит только оставшиеся 5.
- **Редактирование отличается от повтора.** Ревизия — это хеш содержимого; тот же ID с тем же содержимым отбрасывается, с другим — обрабатывается как правка.

Чего мост **не** обещает:

- **Exactly-once при потере ответа.** Если Telegram принял запрос, а ответ не дошёл, узнать это невозможно: Bot API не даёт идемпотентного ключа для `sendMessage`. Такие задачи помечаются как `uncertain`, автоматически **не** повторяются и видны в `/status`. Решение — за тобой (`/retry`).
- **Догон истории после долгого простоя.** Мост зависит от того, что MAX сам пришлёт после реконнекта. Подтверждённого механизма history/sync в протоколе мы не нашли, курсора нет. За время простоя что-то может быть потеряно на стороне MAX.
- **Устойчивость к двум запущенным экземплярам.** Одна папка `state/` — один процесс. Второй экземпляр приведёт к дублям и гонкам за топики.

Сообщение, которое не удалось доставить за `DELIVERY_MAX_ATTEMPTS` попыток, откладывается, а в топик уходит видимая отметка «не доставлено» — чат не встаёт колом и пробел не остаётся незамеченным.

## Что переносится, а что нет

### MAX → Telegram

| Что | Как |
|---|---|
| Текст | Переносится с форматированием: жирный, курсив, зачёркнутый, подчёркнутый, моноширинный, цитата, ссылки |
| Длинный текст | Режется на несколько сообщений по границам разметки, не обрывается |
| Фото | Скачивается и отправляется; несколько подряд от одного отправителя склеиваются в альбом |
| Видео | Полное скачивание через опкод 83; если MAX не отдаёт ссылку — превью-кадр с явной пометкой |
| Документы | Скачиваются, тип определяется по сигнатуре файла, а не по расширению |
| Аудио | Отправляется голосовым сообщением |
| Стикеры | Статичные — как стикер; подпись при этом уходит отдельным сообщением |
| Геопозиция | Нативной точкой на карте (координата `0` — тоже координата) |
| Контакты | Нативной карточкой контакта |
| Цитаты и пересылки | Цитата — превью + нативный reply, если оригинал уже в топике; пересылка — содержимое оригинала. Собственные вложения сообщения доставляются всегда |
| Голосовые нового формата (`_type=UNSUPPORTED`) | Пробуется опкод 88; если не выходит — явная пометка «MAX не отдаёт ссылку» |

### Telegram → MAX

| Что | Как |
|---|---|
| Текст | С форматированием: `STRONG`, `EMPHASIZED`, `STRIKETHROUGH`, `UNDERLINE`, `MONOSPACED`, `LINK` |
| Цитаты и блоки кода | MAX их не поддерживает: блок кода приезжает моноширинным, цитата — обычным текстом |
| Фото | Нативный photo-upload (опкод 80) |
| Альбомы | Уходят **одним** сообщением MAX с несколькими вложениями |
| Документы, видео, аудио | File-upload (опкод 87) |
| Голосовые | Приходят в MAX `.ogg`-файлом, а не голосовым пузырём — нативный опкод не реверсен |
| Статичные стикеры | Как файл |
| Анимированные стикеры | Заменяются своим эмодзи |
| Геопозиция, контакты | Текстом |
| Правки сообщений | Обновляют исходное сообщение в MAX, если мост знает его ID |
| Реакция 👀 | Ставится после подтверждения от MAX |

## Архитектура

```
  MAX WebSocket / Telegram polling
        ↓  валидация и нормализация
  ┌──────────────────────────────┐
  │ durable-журнал (SQLite)      │  ← дедуп, статусы, подтверждённые ID
  └──────────────────────────────┘
        ↓  один воркер на чат
  подготовка медиа (спул на диске, лимиты)
        ↓
  последовательный отправитель → подтверждённые ID / ошибка / uncertain
```

| Модуль | Ответственность |
|---|---|
| `app/main.py` | Сборка всего, сигналы, корректное завершение |
| `app/config.py` | Разбор и валидация настроек до открытия сокетов |
| `app/store.py` | SQLite: журнал доставки, части доставки, карта топиков, манифест |
| `app/pipeline.py` | Планировщик: один воркер на чат, ретраи, восстановление после падения |
| `app/max_client.py` | WebSocket MAX: состояния связи, RPC, watchdog, загрузки |
| `app/max_listener.py` | MAX → Telegram: группировка альбомов, рендер, вложения |
| `app/tg_handler.py` | Telegram: команды и быстрый приём апдейтов в журнал |
| `app/tg_outbound.py` | Telegram → MAX: аплоады и отправка |
| `app/tg_sender.py` | Отправка в Telegram с явным результатом; нарезка текста и альбомов |
| `app/topics.py` | Единственный путь создания/удаления топиков |
| `app/net.py` | Политика исходящих HTTP-запросов, потоковая загрузка в спул |
| `app/resolver.py` | Кеши контактов и чатов с TTL и single-flight |
| `app/health.py`, `app/healthcheck.py` | Состояние связи, счётчики, проба готовности |
| `app/logging_utils.py` | Редактирование секретов до попадания в лог |

## Требования

- Python **3.11+**
- Docker + docker compose v2 (для рекомендуемого деплоя)
- Аккаунт MAX (`web.max.ru`)
- Супергруппа Telegram с **включёнными темами** (Topics / Forum)
- Telegram-бот ([@BotFather](https://t.me/BotFather)) — администратор супергруппы с правом «**Управление темами**»

## Установка

### 1. Подготовка Telegram

1. Создай супергруппу, в настройках включи **«Темы» / «Topics»**.
2. У [@BotFather](https://t.me/BotFather) сделай бота → **`TG_BOT_TOKEN`**.
3. Добавь бота в супергруппу администратором с галкой «Управление темами».
4. Получи **`TG_CHAT_ID`**: перешли сообщение из группы боту [@userinfobot](https://t.me/userinfobot).
5. Получи свой user-id для **`TG_ALLOWED_USER_ID`** (тот же @userinfobot в личке). Без него мост не стартует.
6. В настройках реакций супергруппы разреши «**Все эмодзи**», иначе бот не сможет ставить 👀.

Мост сам проверяет всё это при старте и пишет в лог конкретную причину, если чего-то не хватает.

### 2. Получение токенов MAX

1. Открой [web.max.ru](https://web.max.ru), войди.
2. F12 → **Application** → **Local Storage** → `https://web.max.ru`.
3. Скопируй `__oneme_auth` → **`MAX_TOKEN`**, `__oneme_device_id` → **`MAX_DEVICE_ID`**.

> Этими значениями можно полностью завладеть аккаунтом MAX. В логи моста они не попадают ни на одном уровне логирования, но в `.env` они лежат открытым текстом — права на файл выставь соответствующие.

### 3. Деплой (Docker)

```bash
git clone https://github.com/ircitdev/MAX2TG-Bridge.git max2tg
cd max2tg
cp .env.example .env    # отредактируй
mkdir -p state logs
sudo chown -R 10001:10001 state logs   # контейнер работает не от root
docker compose up -d --build
docker compose logs -f
```

Том `./state` содержит журнал доставки и карту топиков. Потеряешь его — получишь пересозданные топики и, возможно, повторную доставку.

### 4. Локальный запуск

```bash
python -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
cp .env.example .env           # отредактировать
python -m app.main
```

### 5. systemd

`/etc/systemd/system/max2tg.service`:
```ini
[Unit]
Description=MAX2TG-Bridge
After=network-online.target

[Service]
Type=simple
WorkingDirectory=/opt/max2tg
ExecStart=/opt/max2tg/.venv/bin/python -m app.main
EnvironmentFile=/opt/max2tg/.env
Restart=always
RestartSec=10
# Мост обрабатывает SIGTERM: даёт незавершённым отправкам доиграть,
# остальное остаётся в журнале и продолжится после старта.
KillSignal=SIGTERM
TimeoutStopSec=40

[Install]
WantedBy=multi-user.target
```

## Конфигурация `.env`

Полный список с комментариями — в [`.env.example`](.env.example). Главное:

| Переменная | Обязательная | Описание |
|---|---|---|
| `MAX_TOKEN` | да | `__oneme_auth` из Local Storage |
| `MAX_DEVICE_ID` | да | `__oneme_device_id` оттуда же |
| `TG_BOT_TOKEN` | да | Токен бота |
| `TG_CHAT_ID` | да | ID супергруппы (`-100…`) |
| `TG_ALLOWED_USER_ID` | да¹ | Кто может писать от твоего имени. Несколько — через запятую |
| `TG_ALLOW_ANY_MEMBER` | да¹ | Альтернатива: явно разрешить всей супергруппе |
| `TG_ADMIN_USER_ID` | нет | Отдельные права на управление топиками |
| `TG_STATUS_CHAT_ID` | нет | Куда слать статусы моста (обычно — себе в личку) |
| `MAX_CHAT_IDS` | нет | Фильтр **входящих** чатов. Это маршрутизация, не граница доступа |
| `TG_DROP_PENDING_UPDATES` | нет | По умолчанию `false` — накопившиеся апдейты не выбрасываются |
| `MEDIA_ALLOWED_HOSTS` | нет | С каких хостов можно качать вложения |
| `MEDIA_TRUSTED_NETS` | нет | Диапазоны, которые не считаются «приватными» при проверке адресов. Нужен за роутером с fake-IP DNS: `198.18.0.0/15` |
| `SQLITE_SYNCHRONOUS` | нет | `FULL` по умолчанию |
| `JOURNAL_RETENTION_DAYS` | нет | Сколько хранить записи о доставленном (14) |
| `LOG_MESSAGE_TEXT` | нет | Писать ли тексты сообщений в лог. По умолчанию нет |

¹ Нужно указать **одно из двух**, иначе мост откажется стартовать с объяснением.

## Команды бота

Работают только в супергруппе `TG_CHAT_ID` и только у разрешённых пользователей. Анонимные админы и посты от имени канала отклоняются — у них нет личности, которую можно проверить.

| Команда | Что делает |
|---|---|
| `/bind <chat_id или URL> [название]` | Привязать топик к чату MAX |
| `/add <https://max.ru/join/...>` | Открыть групповую ссылку MAX и создать топик |
| `/profile` | (в топике) Профиль собеседника |
| `/intro` | (в топике) Перепостить карточку, обновив кеш |
| `/del` | (в топике) Удалить топик и снять связь (с подтверждением) |
| `/status` | Состояние связи, очередей, счётчики |
| `/retry [here]` | Повторить провалившиеся отправки |
| `/help` | Справка |

## Эксплуатация

### Что смотреть в `/status`

- **Состояние связи** — `ready` значит, что MAX подтвердил авторизацию, а не просто что сокет открыт.
- **Самое старое незавершённое** — растёт, значит доставка встала, даже если связь «живая».
- **провалено / неизвестно** — разбирать через `/retry`. «Неизвестно» означает, что повтор может создать дубль.

### Health-check

Контейнер публикует пробу готовности: она проверяет свежесть снимка состояния, факт авторизации в MAX и возраст очереди. Обрати внимание: обычный `docker compose` **сам по себе не перезапускает** unhealthy-контейнер — это сигнал для `docker ps`, внешнего мониторинга или планировщика.

```bash
docker compose exec max2tg python -m app.healthcheck; echo $?
```

### Что смотреть в логах

- `Accepted message id=… lag=…` — кадр принят. `lag` считает разницу часов MAX и наших: большое значение — подсказка, а не доказательство, что задержка была на стороне MAX.
- `Replay of … — already journalled` — повтор отсечён журналом.
- `MAX link state: X → Y` — переходы машины состояний связи.
- `Job … is uncertain` / `failed permanently` — требует внимания.
- `Liveness watchdog: …` — связь признана мёртвой и переустанавливается.

`LOG_LEVEL=DEBUG` включает подробный режим. Токены и подписи в URL редактируются на любом уровне; тексты сообщений не пишутся, пока не включишь `LOG_MESSAGE_TEXT=true`.

### Резервное копирование

```bash
docker compose stop max2tg
cp -a state state-backup-$(date +%F)
docker compose start max2tg
```

Проверь восстановление хотя бы раз, на отдельной конфигурации: бэкап, который никогда не разворачивали, — это не бэкап.

## Известные ограничения

1. **Голосовые TG → MAX** уходят `.ogg`-файлом: опкод нативной voice-загрузки не реверсен ([vkmax#14](https://github.com/nsdkinx/vkmax/issues/14)).
2. **Голосовые MAX → TG** нового формата (`_type=UNSUPPORTED`) скачиваются не всегда — пробуется опкод 88, при неудаче в топик уходит явная пометка.
3. **Ссылки `/u/<token>`** `/add` не открывает: опкод 57 ищет их в пространстве чатов. Обходной путь — открыть ссылку в MAX, топик создастся при первом сообщении.
4. **Лимит 20 МБ** — это ограничение на **скачивание** файла ботом через `getFile`, то есть на направление TG → MAX. Отправлять в Telegram мост может файлы крупнее; потолок задаётся `MEDIA_MAX_BYTES`.
5. **Кастомные эмодзи как реакции** ботам запрещены, используется 👀.
6. **Телефон и «о себе»** `CONTACT_GET` не возвращает вовсе — в `/profile` их не будет.
7. **Ротация токена MAX** — при логине с другого устройства токен может стать невалидным. Мост различает «MAX отклонил токен» (нужен новый `MAX_TOKEN`) и «авторизация не завершилась» (похоже на сеть) и пишет об этом разными сообщениями.
8. **Автообновление токена не реализовано** — есть ли оно в протоколе вообще, не проверено.
9. **Сообщения, отправленные тобой из самого приложения MAX, в Telegram не приезжают.** Это осознанный выбор: отличить эхо собственного ответа через мост от сообщения, написанного в MAX вручную, по данным протокола нельзя, поэтому отсекаются все собственные.
10. **Один экземпляр на одну папку `state/`.** Выборов лидера нет.
11. **Догон истории после простоя** не реализован — см. [Гарантии доставки](#гарантии-доставки).

## Разработка

```bash
pip install -r requirements-dev.txt
pytest -q          # 701 тест
ruff check app tests
```

Тесты покрывают журнал и дедупликацию, планировщик (ретраи, порядок, восстановление после падения), транспорт MAX против **настоящего локального WebSocket-сервера** (таймауты авторизации, half-open, обрыв во время RPC, битые кадры), нарезку HTML и альбомов, политику исходящих запросов, авторизацию Telegram и редактирование секретов в логах.

CI прогоняет тесты на Python 3.11–3.13, отдельно на нижних границах версий зависимостей, собирает Docker-образ и проверяет, что внутри него импортируются все модули.
